## Decisions locked this week

### D-W22-01: Three-KPI metric governance

KPIs the project commits to optimize:

1. **Efficiency**: fixed 150-PDF wall_seconds + s/PDF + p95.
2. **Pass rate**: `pass_rate @ scorer-vX` with the scorer version pinned in `release_manifest.jsonl`.
3. **Scorer health** (independent oracle): `scorer-vX vs human-label` Cohen's κ on a sealed holdout.

Optimizing (1) or (2) without (3) staying flat or rising = Goodhart violation. KPI (3) is owned by whoever maintains the scorer and is not visible to the pipeline-optimization loop.

Source: `docs/ocr-quality-strategy.md §13`. Reviewed against FinePDFs precedent: their model card explicitly warns against using `score >= threshold` for curation; we accept that warning and route grey-band docs to human review instead.

### D-W22-02: Component-versioning architecture

Independent-cadence components (`pdfsys-parsers` first, `pdfsys-quality-scorer` next) move to dedicated git repos, mounted in the main repo as submodules under `external/`. A new `system_release.toml` pins each component to a 40-char commit SHA + human-readable tag. A new `pdfsys release {status,lock,verify}` CLI maintains it.

This gives every system release a **bill of materials**: exactly one `system.version` ↔ one tuple of `(parsers commit, scorer commit, main commit)`. Drift is caught by `pdfsys release verify` in CI.

Source: `docs/superpowers/specs/2026-05-30-parsers-submodule-design.md`.

### D-W22-03: Extraction order

Parsers first, scorer second. Parsers already have an HTTP boundary (commits `3847b6f` + `375c9a2`) so the extraction is pure repo split + tooling, no new abstraction. Process is rehearsed on the lower-risk component before being applied to the scorer, where it carries §13 anti-hack obligations.
